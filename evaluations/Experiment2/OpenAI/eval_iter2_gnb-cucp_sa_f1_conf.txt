Analyzing compliance against O-RAN, 3GPP, and ETSI security standards for CU-CP:

1. ciphering_algorithms = ("nea0"):
   - According to 3GPP TS 33.501 and 38.331, nea0 means no encryption.
   - Security risk: "nea0" is null ciphering, effectively no ciphering.
   - For over-the-air security and especially transport layer confidentiality, the configuration must not prefer "nea0" (no encryption).
   - Therefore, this is a security violation.

2. integrity_algorithms = ("nia2", "nia0"):
   - "nia0" means no integrity protection.
   - The first algorithm "nia2" is a valid integrity algorithm, no violation here because the UE picks the first supported.
   - Leaving "nia0" second is acceptable as fallback; not violation.

3. drb_ciphering = "yes"
   - Ciphering enabled for DRBs, which is good.

4. drb_integrity = "no":
   - Integrity protection disabled on DRBs, which is a known risk.
   - According to 3GPP spec, DRB integrity protection should be enabled to protect user plane data.
   - Violation.

5. amf_ip_address = ({ ipv4 = "oai-amf"; })
   - The "ipv4" field has a string hostname "oai-amf".
   - The configuration is expected to have an IP address, not a hostname.
   - Using a hostname instead of IP can cause name resolution issues or risk the use of invalid/unverified addresses.
   - While not strictly a security violation, it is an operational risk.
   - The spec does not forbid hostname, but minimal security best practice: keep IP addresses.
   - Not explicitly mandated as a violation here, so we do not treat as a must-fix.

6. remote_s_address = "0.0.0.0"
   - According to the comment, it means multiple DUs.
   - Not a security violation.

7. SCTP streams count:
   - 2 streams in/out minimal for SCTP.
   - No violation present.

- ciphering_algorithms includes "nea0" first → No encryption chosen by default.
- drb_integrity = "no" → integrity protection disabled on DRBs.
